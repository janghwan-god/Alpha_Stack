## 2. 왜 했나

강사님 README 는 **운영 안내서**다. 요구사항 → 환경 파일 → 키 → 실행 → 접속 → 종료가
번호로 이어지고, 정보가 거의 다 표에 들어 있다. 우리 README 는 **서사**였다. 왜 만들었고
무엇을 배웠는지는 잘 적혀 있는데, 정작 *"클론해서 뭘 치면 되나"* 와 *"이 폴더들은 뭔가"* 가
없었다. 341개 파이썬 파일짜리 저장소인데 **저장소 구조 트리가 없었다.**

둘은 경쟁하지 않는다. 자리가 다를 뿐이다. 그래서 서사를 앞에, 운영 안내를 뒤에 두고
그 사이에 독자별 진입 경로를 깔았다.

## 5. 막힌 것 · 남은 것

**mermaid 를 두 번 고치고 결국 버렸다.** 처음 렌더는 한글이 낱말 한가운데서 끊겼고
("예/탁결제원", "레/포"), 화살표 라벨 둘이 겹쳤다. `<br/>` 로 줄바꿈을 직접 지정하고
라벨을 줄여 고쳤더니 그건 나았는데, **세로가 가로의 1.2배**(1568×1880)로 남았고
`common/` 과 금지 경로의 점선이 캔버스 오른쪽을 크게 휘감아 돌았다. README 에서는
가로폭에 맞춰 줄어들어 글자가 작아진다.

계층도는 **사람이 층을 정해 두는 그림**이라 자동 배치가 할 일이 거의 없다. 손으로

## 6. 배운 것

- **문서를 다시 쓰는 일은 문서 작업이 아니라 실측 작업이었다.** 낡은 숫자 넷과 회귀 하나가
  나왔는데, 넷 다 "문장을 다듬다가" 나온 게 아니라 **숫자를 다시 재서** 나왔다. 옮겨 적기만
  했으면 전부 그대로 실렸을 것이다.
- **한 저장소 안에서도 숫자가 갈린다.** `ruff` 는 배지가 209, 본문 표가 220 이었다. 같은 날
  다른 자리를 고치면 이렇게 된다. 숫자를 여러 곳에 쓰려면 **한 번에 같이 고칠 수 있게**
  가까이 두거나, 아예 한 곳에만 두어야 한다.
- **약점을 배지로 광고하지 않는다 — 대신 설명이 따라다니는 자리에 적는다.** `ruff-209-orange`
  배지의 해명("형식만입니다")은 본문 152줄에 있었고 배지를 따라다니지 않았다. 지금은 숫자를
  실측표와 "알려진 한계"에 넣었다. 지우는 것과 옮기는 것은 다르다.
- **자동 배치가 늘 이기지는 않는다.** mermaid 는 흐름도에는 좋지만, 층이 이미 정해진 그림에서는
  사람이 놓는 편이 낫다. "예쁨"은 3D 나 그라데이션이 아니라 **색 수를 줄이고 · 방향을 하나로
  통일하고 · 구역에 이름을 붙이는 것**이었다.
- **두 미러에서 갈리는 문법은 미리 확인하고 쓴다.** `<picture>` 는 GitHub 에서 다크모드를
  주고 GitLab 에서는 벗겨진다. 다행히 안쪽 `<img>` 가 살아남아 **깨지지 않고 강등**된다 —
  이걸 문서로 확인하고 나서야 쓸 수 있었다. 확인 안 하고 썼으면 GitLab 쪽이 빈칸이 됐을 수도 있다.
- **끝물에 찾은 결함은 고치는 대신 적고 넘긴다.** `action` · `in_cooldown` 이 원장에 남아야 하는
  칸인지 화면용 중간값인지는 백테스트 파트의 설계 의도다. 원인·재현·두 선택지를 이슈에 적고
  닫았다. 고치지 않기로 한 것과 모르고 지나친 것은 다르다 — 그 차이를 남기는 게 기록의 일이다.
